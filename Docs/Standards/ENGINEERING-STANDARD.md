# 《天命西游／QQ西游》工程与代码规范

> 状态：Mandatory  
> 版本：V1.0  
> 日期：2026-08-26  
> 适用范围：`Rebuild` 中全部手写 C++、UE、CMake、Protobuf、SQL、脚本、测试和部署代码  
> 原则：规范由 CI 执行，不依赖个人记忆

---

## 1. 完成定义

代码只有同时满足以下条件才算完成：

1. 放在正确模块，依赖方向合法。
2. 文件、类型和函数职责单一，未突破规模硬限制。
3. 格式化、编译警告、静态分析、架构测试、单元/契约/集成测试通过。
4. 错误、日志、指标、安全和配置行为明确。
5. 公共契约、数据库 Migration 和行为变化有文档。
6. 没有新增明文 Secret、未锁定依赖、平台硬编码或临时 TODO 债务。
7. 至少一名非作者完成评审；核心协议、经济和迁移代码需双人评审。

“能运行”不是完成，“以后再拆”不能作为合并巨型文件的理由。

## 2. 文件和复杂度硬限制

### 2.1 文件规模

| 对象 | 目标 | CI 警告 | CI 硬失败 |
|---|---:|---:|---:|
| 手写头文件 `.h/.hpp` | ≤ 250 行 | > 300 行 | > 500 行 |
| 手写实现 `.c/.cc/.cpp` | ≤ 500 行 | > 600 行 | > 1000 行 |
| UE Build/Target/C# 文件 | ≤ 250 行 | > 300 行 | > 500 行 |
| CMake 文件 | ≤ 250 行 | > 300 行 | > 500 行 |
| 单个 SQL Migration | ≤ 300 行 | > 500 行 | > 1000 行 |
| PowerShell/Python 工具文件 | ≤ 500 行 | > 700 行 | > 1000 行 |

统计忽略空行和纯注释，但不会忽略预处理器或宏。生成代码、第三方源码和冻结的 Legacy 证据目录可以豁免；豁免目录必须在 CI 配置中显式列出，产品手写代码不能假冒生成代码。

### 2.2 函数与类型

| 指标 | 目标 | 硬限制/处理 |
|---|---:|---|
| 函数逻辑行 | ≤ 40 | > 60 警告；> 100 失败 |
| 圈复杂度 | ≤ 10 | > 15 失败 |
| 嵌套深度 | ≤ 3 | > 4 失败 |
| 显式参数数量 | ≤ 4 | > 5 使用参数对象或拆职责 |
| 类公开方法 | ≤ 12 | > 15 需要拆分或 ADR |
| 一个头文件的主要公开类型 | 1 | 小型紧密值类型可例外 |

巨大 `switch`、协议分发和自动生成映射必须数据驱动或生成；不得用单个数千行函数承载全部消息。

### 2.3 例外流程

无法立即满足硬限制时：

- 新增 `Docs/Waivers/WVR-xxxx.md`；
- 写明文件、原因、风险、负责人、拆分方案和到期日期；
- 到期自动使 CI 失败；
- 安全、经济、协议解析和数据库事务代码不得以“历史原因”永久豁免。

## 3. 模块和目录规则

每个模块至少包含：

```text
module-name/
├─ include/tmxy/<module>/       公开头文件
├─ src/                         私有实现
├─ tests/                       单元/组件测试
├─ CMakeLists.txt
└─ README.md                    职责、公开 API、依赖、所有者
```

规则：

- 默认私有；只有稳定契约进入 `include/`。
- 禁止从其他模块 include `src/`。
- 每个目录只能有一个清晰领域含义，不能使用 `misc`、`common2`、`temp`、`new`、`backup`。
- `foundation` 只放无业务含义的基础类型，不接收“暂时不知道放哪”的代码。
- `apps/*` 只做依赖注入、启动、信号、配置和生命周期，不写业务规则。
- `adapters/*` 封装第三方和基础设施；一个适配器不能同时实现数据库、网络和业务。
- `Contracts/generated` 只放生成物；修改必须从源 Schema 重新生成。
- Legacy 源码不能被新模块 include，只能由研究工具读取或由测试向量表达行为。

依赖方向由 CMake target 和架构测试检查，禁止用相对路径绕过 target 边界。

## 4. C++20 规则

### 4.1 必须使用

- RAII 和确定所有权。
- `std::unique_ptr` 表达唯一所有权，`std::shared_ptr` 仅在真实共享生命周期中使用。
- `std::span`、`std::string_view` 表达非拥有视图，但不得跨越来源生命周期。
- `std::chrono` 表达时间和时长。
- `std::uint32_t` 等定宽类型表达协议、数据库和持久化字段。
- 强类型 ID，如 `CharacterId`、`ItemId`，禁止用裸 `int` 在领域间传递。
- `enum class` 和显式底层类型。
- `[[nodiscard]]` 标注不能忽略的 Result/状态。
- `const`、不可变值对象和窄作用域。

### 4.2 禁止使用

- 拥有资源的裸指针和手写 `new/delete`。
- C 风格强制转换、可变全局状态和 Singleton Service Locator。
- `using namespace` 出现在头文件。
- 把异常穿越网络、线程、插件、C ABI 或进程边界。
- 直接序列化内存结构或依赖 `#pragma pack` 作为协议格式。
- 在 Domain/Application include `windows.h`、Asio、libpq、UE 或 OpenTelemetry SDK。
- 宏实现业务逻辑；宏只用于平台/编译器边界和受控反射接口。
- 未说明所有权的 `void*`、未检查的下标、无边界 `memcpy/sprintf`。

### 4.3 错误模型

- 可预期业务失败使用强类型 `Result<T, Error>`/状态，不使用异常控制流程。
- 构造不变量失败、不可恢复编程错误可断言；不得用断言处理用户输入。
- 基础设施错误转换为稳定错误类别，保留内部诊断，不向客户端泄露 SQL/路径/Secret。
- 每个错误拥有稳定代码、可观测字段和是否可重试语义。
- 不捕获后静默忽略；降级必须有日志、指标或明确返回值。

## 5. 命名和文件组织

### 5.1 C++ 命名

| 对象 | 规则 | 示例 |
|---|---|---|
| namespace | `snake_case` | `tmxy::character` |
| 类型/枚举 | `PascalCase` | `CharacterRepository` |
| 函数/方法 | `snake_case` | `load_character` |
| 局部变量/参数 | `snake_case` | `character_id` |
| 成员变量 | `snake_case_` | `connection_pool_` |
| 常量 | `kPascalCase` | `kMaximumFrameBytes` |
| 文件 | `snake_case.hpp/.cpp` | `character_repository.cpp` |
| Protobuf message | `PascalCase` | `CreateCharacterRequest` |
| Protobuf field | `snake_case` | `character_id` |
| SQL 对象 | `snake_case` | `economy.inventory_item` |

UE 类型遵循 UE 强制前缀和反射命名；UE 模块内部仍遵守职责、规模和依赖规则。

### 5.2 文件顺序

实现文件按以下顺序：

1. 对应头文件；
2. C/C++ 标准库；
3. 第三方库；
4. 本项目公开头；
5. 本模块私有头。

头文件自包含并使用 `#pragma once`。禁止依赖偶然 include 顺序。

## 6. 网络和并发规范

- I/O 回调只做解析、校验和投递，不执行长业务或阻塞数据库查询。
- 每个连接拥有明确状态机、读写队列上限、超时、取消和关闭路径。
- 所有外部长度先检查再分配；最大帧长由协议常量和测试固定。
- 共享状态优先通过 actor/strand/单写者模型管理；使用锁时记录不变量和锁顺序。
- 禁止持锁执行网络、数据库、磁盘或外部回调。
- Task/Coroutine 捕获对象生命周期必须明确；取消后不能访问销毁对象。
- 每个并发 Bug 修复必须增加可重复测试或故障注入。

---

## 7. PostgreSQL 和 SQL 规范

- 业务代码禁止 SQL；SQL 只出现在 `persistence_postgres` 或版本化 Migration。
- 全部动态值参数化；表名/列名只能来自编译期白名单。
- `SELECT *` 禁止进入产品查询。
- 查询显式列、Schema、排序和分页边界。
- 每条写入明确事务、锁、幂等键和受影响行数预期。
- 物品、货币、商城和邮件领取写入必须同时生成不可变审计记录。
- Schema 使用 `snake_case`，主键和外键类型一致。
- 时间用 `timestamptz`/UTC；金额和数量用整数；JSONB 只用于演进型非核心字段，不能替代关系模型。
- Migration 不能依赖人工执行顺序之外的隐含状态；CI 必须从空库和上一发布库各升级一次。
- Repository 返回领域值，不返回 `PGresult`、行对象或数据库可空语义。
- 慢查询预算、行数估算和索引依据进入测试/评审，不凭感觉加索引。

---

## 8. Protobuf 和契约规范

- `.proto` 是消息契约唯一来源；生成文件只读。
- 已发布字段号永不复用；删除字段必须 `reserved`。
- 每个外部消息有明确版本、权限、最大大小、幂等性和错误集合。
- 不使用 Protobuf map 表达需要稳定顺序或强约束的核心数据。
- 不把数据库行结构直接暴露为公网协议。
- 所有消息至少有正常、边界、未知字段、截断和超限测试。
- 兼容策略默认“新增可选字段、旧消费者忽略未知字段”；破坏变更使用新消息/主版本。

---

## 9. UE 代码边界

- Widget 只处理显示状态和用户意图，不直接组装网络包或访问数据库语义。
- `TMXYNet` 将 Protobuf/传输结果转换为客户端应用事件。
- `TMXYGameplay` 不 include Editor/Importer。
- 原始 Package/TBL/资产解码只存在 Editor 插件或独立工具，Shipping 禁止包含。
- Gameplay UObject/Actor 控制生命周期时使用 UE 所有权模型；非 UObject 逻辑优先普通 C++ 值类型。
- Blueprint 用于表现编排和可调参数，权威协议、存档、经济与复杂算法使用受测试 C++。
- 每个公开 Blueprint API 有类别、说明、失败行为和线程限制。

---

## 10. 日志、指标和隐私

- 日志使用结构化字段，不拼接难以查询的整段文本。
- 每个请求携带 `request_id/correlation_id`；跨服务延续 Trace Context。
- 日志不得包含密码、Token、完整连接串、私钥、支付信息或可复用验证码。
- 账号/角色标识按最小需要记录；面向外部的错误不泄漏内部表名和 SQL。
- 错误日志必须可行动：操作、稳定错误码、实体 ID（可记录时）、依赖、重试状态。
- 高频循环禁止逐帧/逐包 Info 日志；使用采样、计数器或聚合。
- 指标标签禁止使用账号、角色、请求 ID 等无界高基数字段。

## 11. 测试要求

| 代码类型 | 合并前最低测试 |
|---|---|
| Domain 规则 | 单元测试：正常、边界、不变量、错误 |
| Application 用例 | Port fake + 用例测试 + 权限/幂等 |
| PostgreSQL Adapter | 真实 PostgreSQL 容器集成测试；禁止仅 mock SQL |
| 网络解析 | 固定向量、截断、超长、Fuzz/属性测试 |
| Protobuf 契约 | 兼容、未知字段、最大尺寸、错误码 |
| Migration | 空库 Up、上一版 Up、校验、备份恢复/补救 |
| 经济写入 | 并发、重复、失败回滚、总量守恒、审计 |
| UE 功能 | 自动化/功能测试 + 必要 Golden 截图 |

覆盖率不是唯一质量指标，但新 Domain/Application 行覆盖率目标 ≥ 85%，分支覆盖率目标 ≥ 75%；安全、协议解析、经济事务的核心路径必须 100% 场景覆盖。

## 12. CI 强制门禁

每个 PR 按顺序执行：

1. 文件归属和禁止目录检查。
2. 文件/函数/复杂度阈值检查。
3. `clang-format --dry-run`。
4. CMake configure 和依赖 lock 校验。
5. Linux Clang 编译，警告视为错误。
6. Windows MSVC 跨平台编译（后端非发布权威，但必须保持可开发）。
7. `clang-tidy` 与安全规则。
8. 单元、架构、契约测试。
9. PostgreSQL 18 Migration/Repository 集成测试。
10. UE 相关目标的 Build/Automation 测试。
11. Secret、依赖漏洞、许可证和容器镜像扫描。
12. 生成 SBOM、测试报告和构建元数据。

主分支不得通过“暂时关闭 CI”合并。Flaky Test 视为缺陷：隔离必须有负责人、Issue 和到期日。

## 13. 评审清单

评审者至少回答：

- 代码属于正确领域和层吗？
- 是否引入跨层、跨领域或第三方类型泄漏？
- 文件/类/函数是否承担多个职责？
- 能否删除、组合或用数据驱动方式降低复杂度？
- 错误、重试、幂等、超时和取消是否明确？
- 是否存在数据库并发、重复写、部分提交或审计缺口？
- 外部输入是否有长度、范围、权限和资源上限？
- 日志是否足够诊断且不泄漏 Secret？
- 测试是否验证行为，而非只覆盖实现行？
- 文档、Migration、Schema、协议和部署是否同步？

---

## 14. 遗留代码规则

- `ClientCode`、`ServerCode`、`ToolCode` 不受新格式化器修改，继续只读。
- 从遗留源码提取的规则必须以新命名、新模块边界和测试重新实现，不能整文件复制后逐步修。
- 需要引用遗留片段时，在设计/测试中记录源路径和 Manifest 哈希，不在新生产文件保留大段注释掉的旧代码。
- 禁止 `Old/New/New2/Final/Final2` 类命名；版本通过 Git、Schema 和协议表达。
- Legacy Adapter 只能位于工具或测试边界，不能成为新业务的永久依赖。
